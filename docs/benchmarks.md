# Benchmarks

How the correctness and performance claims in this repository are measured, and what they don't claim.

## Why benchmark this project

"Route generation succeeded" isn't a single pass/fail bit. A route can come back and still be wrong along several independent dimensions: is it close enough to the requested distance, is the graph traversal actually connected, did the API return the number of alternatives it was asked for, are those alternatives meaningfully different from each other, and, for facility requests, was the requested stop actually encountered where it was supposed to be rather than just present somewhere nearby? Each suite below targets one of those dimensions with a deterministic, reproducible scenario set instead of a single aggregate score.

## Core local-engine suite

Source: [`backend/benchmarks/local/report_20260825_185757.md`](../backend/benchmarks/local/report_20260825_185757.md). 537 deterministic scenarios across round / out-and-back / mixed shapes, generated by `scripts/benchmark_suite.py` against `app.generation.engine`'s `generate_candidates` and `generate_amenity_aware`. This is the local-generation benchmark, not the generic multi-facility `/routes` contract; a subset of scenarios exercise legacy-style offline fountain placement (the 268/268 figure below), not the current `facility_requirements` list.

| Metric | Result |
|---|---|
| Scenarios with ≥1 route within ±100 m of target | 537/537 |
| Disconnected candidates | 0 |
| Candidates inspected | 2,680 |
| Median / p95 / max generation latency | 0.345 s / 1.805 s / 3.067 s |
| Offline fountain-placement checks | 268/268 |
| Scenarios with ≥1 meaningfully distinct alternative | 100% |
| All candidate pairs at/below 0.80 overlap | 93.8% (5,022/5,352 pairs) |
| Pooled median pairwise segment overlap | 0.040 |

**Reading these numbers:** "537/537" is scenario-level success: every scenario produced at least one qualifying route. It doesn't mean "537 routes were generated" (2,680 candidates were actually inspected across those scenarios). Distance success is measured against a ±100 m tolerance on the requested distance.

**Diversity metric:** each route is represented as the set of undirected consecutive segments in its rendered geometry (endpoints rounded to six decimal places); overlap between two routes is the Jaccard index over those segment sets. A pair at or below 0.80 overlap counts as meaningfully distinct. Out-and-back routes retrace most of their own outbound path by definition, so high self-overlap there is expected and isn't comparable to round/mixed routes.

The report also carries a set of descriptive geometry metrics (max start distance, isoperimetric quotient, elongation ratio, sharp turns per km) captured as a baseline ahead of round-generator changes; those are observability, not a pass/fail gate.

## Route-count reliability

Source: [`backend/benchmarks/local/count_reliability_20260825_183354.md`](../backend/benchmarks/local/count_reliability_20260825_183354.md)

The core suite only required at least one qualifying route per scenario; it never asserted that the number returned matched the number requested, which is exactly the kind of gap a route-count regression can hide in. This suite closes that blind spot by re-running the same 537 scenarios through the real product code path at the live default of 3 requested alternatives:

| Metric (requested count = 3) | Result |
|---|---|
| Scenarios returning exactly the requested count | 100.0% |
| Scenarios where all returned routes were within ±100 m | 99.8% |
| Both of the above simultaneously | 99.8% |
| Individual candidates within ±100 m | 99.9% |

As a secondary stress figure, requesting 5 alternatives instead of the product-default 3 across the same scenarios yielded 98.9% exact-count, 99.4% all-within-tolerance, and 98.7% satisfying both. This is not the live product default.

## Facility constraint benchmark

Source: [`backend/benchmarks/facilities/report_20260825_184658.md`](../backend/benchmarks/facilities/report_20260825_184658.md). Three strata, each testing a different question about cumulative-mile facility constraints.

**Stratum A: mechanism correctness.** Fixtures are placed at the exact point a real reference route's own geometry already passes at the target mile marker, so a solution is guaranteed to exist. 117 scenarios across 0 to 6 simultaneous requirements: **117/117 fully constraint-valid**. This confirms the encounter-matching and deterministic-assignment mechanism correctly recognizes an achievable cumulative-mile stop. It says nothing about whether arbitrary real-world facility placement is always jointly routable, since these fixtures are natural-match-friendly by design.

**Stratum B: planner stress.** Fixtures are placed at real graph nodes near the requested window's radial (straight shortest-path-from-start) distance instead of on any candidate's own geometry, and rejected and re-picked if an ordinary natural-match pool already happens to cover them. This is the number that measures whether the constrained planners are doing real work:

| Simultaneous hard requirements | Fully constraint-valid |
|---|---|
| 1 | 18/18 (100%) |
| 2 | 0/18 (0%) |
| 3-4 | 0/18 (0%) |
| 5-6 | 0/18 (0%) |

A single hard requirement is recovered every time. Two or more simultaneous hard requirements aren't currently solved by the bounded beam search; this is a measured search-space limitation, documented rather than hidden. See [`architecture.md`](architecture.md#known-technical-boundary). (The 5-6 row's "fully constraint-valid" count of 0/18 is a scenario-level all-or-nothing figure. The report separately tracks individual per-requirement satisfaction across the same 18 scenarios, which is a different, non-zero measurement; the two answer different questions and aren't in conflict.)

**Stratum C: real committed water-dataset coverage.** No synthetic fixture placement, just the actual bundled OSM water extract exercised exactly as a live request would. 12/12 scenarios fully constraint-valid, 18/18 individual water requirements found, median latency 6.75 s (max 10.23 s). This is a small, narrow sample (2 starting areas × 3 distances × 1-2 requirements): a coverage measurement for that specific sample, not a claim about water-facility coverage everywhere in Manhattan. Restroom data is Supabase-only and isn't represented in any offline benchmark.

## Round-generator migration re-evaluation (2026-08-28)

`ROUND_GENERATOR` selects the generator behind every ordinary round candidate pool, for explicit `shape="round"` and `shape="mix"`'s round component alike (see [`architecture.md`](architecture.md)). Earlier evaluations were gated on a stale full-suite p95 latency figure (2.27s) measured before [`FacilitySpatialIndex`](../backend/app/facilities/spatial_index.py) replaced O(facilities x segments) encounter scoring, the actual dominant cost on real multi-facility requests. This section is a same-commit re-evaluation after that change, run on this repository's `backend/scripts` suites.

**Result: `v1` remains the default.** Polygon's geometry is substantially better, and, after the reliability fix below, its correctness at the product's count=3 default matches or beats v1. Two gaps remain:

1. **Full-suite p95 latency** (2.295s) is still above the historical <2.0s raw-generation gate, on a small, well-characterized subset of scenarios.
2. **Round-shape reliability at the API's supported count=5** (~90.0% all-within-tolerance) is meaningfully below v1's ~98.9%. This is a measured gap at a request shape the API actually serves, not just a count=3 footnote.

The switch (`ROUND_GENERATOR=polygon`) stays an explicit opt-in rather than the default until both gates close.

**Fixes made along the way, landed regardless of the default decision:**
- `app/generation/reuse_penalty.py`'s edge-weight callback (the hottest function in every reuse-penalized Dijkstra call) was allocating a `frozenset` and a throwaway generator on every edge relaxation. Replaced with plain `(min, max)` tuples and a fast path for the common single-parallel-edge case. This latency win applies regardless of generator; it dropped v1's full-suite p95 from 1.991s to 1.543s in addition to helping polygon.
- Polygon's own candidate ranking (`polygon_loop_pairs`) sorts purely by roundness (isoperimetric quotient), with no forced convergence mechanism (it never splices a spur, unlike v1). On this commit that left round-shape "all 3 returned candidates within +/-100m" at only 84.4% (vs v1's 99.4%), concentrated in narrow local topology (Inwood, Washington Heights, Hamilton Heights) at larger target distances, where several of the 10 templates can't close to within tolerance at any scale in their search bounds. `engine._round_pairs` now ranks polygon's own pool in-tolerance-first and tops it up with a small, shortfall-sized v1 fallback whenever polygon alone can't supply `MIN_WITHIN_TOLERANCE_FLOOR` (5, the API's max product count) in-tolerance candidates. This top-up only fires on the same narrow subset of hard scenarios, confirmed by measurement.

**V1 (current default, same commit) vs polygon (opt-in), full 537-scenario suite (`scripts/benchmark_suite.py`, count=5 per scenario):**

| Metric | v1 (default) | polygon (`ROUND_GENERATOR=polygon`) |
|---|---|---|
| Scenarios succeeding | 537/537 | 537/537 |
| Within +/-100m of target | 537/537 (100.0%) | 536/537 (99.8%) |
| Median latency | 0.318s | 0.468s |
| p95 latency | **1.543s** (PASS <2.0s) | **2.295s** (FAIL <2.0s) |
| Max latency | 2.605s | 3.285s |

The p95 gap is concentrated in a handful of scenarios, not spread evenly across all 537. The "Battery Park tip, huge target" hard case (a 12mi round loop from a peninsula tip) takes 1.258s under v1 alone and 2.295s under polygon alone: both generators are independently expensive there (large search radius, constrained topology), and the reliability fallback pays for both when polygon's own yield is thin, compounding the cost on exactly this kind of scenario. Median and p90 latency stay strong under polygon.

**Geometry: polygon is better across the round population** (`scripts/benchmark_polygon_loop.py`, 91 matched round/non-amenity scenarios; see the generated report for the full breakdown):

| Metric | v1 median | polygon median |
|---|---|---|
| isoperimetric quotient (compactness, higher=rounder) | 0.160 | 0.465 |
| elongation ratio (lower=more balanced) | 5.13 | 1.41 |
| radial exposure (lower=stays closer to home) | 0.404 | 0.299 |
| short_start_return_spur rate | 3.3% | 0.0% |

**Count reliability at the product default (count=3), real `plan_routes` path (`scripts/benchmark_count_reliability.py`):**

| Metric (round shape, count=3) | v1 | polygon |
|---|---|---|
| Exact requested count | 100.0% | 100.0% |
| All returned within +/-100m | 99.4% | **100.0%** |
| p95 latency | 0.921s | 1.553s |

**At count=5, an API-supported request shape, the gap is real and unresolved**: round-shape all-within-tolerance is only 90.0% under polygon vs v1's 98.9%. `MIN_WITHIN_TOLERANCE_FLOOR` (5) is sized to guarantee the product's count=3 default, not count=5; at count=5 the pool needs every one of its 5 returned slots in tolerance, a stricter bar the current fallback threshold doesn't target. This is the second reason, alongside p95 latency, polygon isn't yet the default. Closing it would mean either raising the floor (more fallback triggers, more latency) or a deeper fix to polygon's own per-template convergence, both out of scope for this migration.

**Facility benchmark (`scripts/benchmark_facilities.py`)**: unchanged from the documented baseline above: Stratum A 117/117, Stratum B 18/18 -> 0/18 -> 0/18 -> 0/18 (2.8% partial), Stratum C 12/12. The constrained multi-facility planner (which already used polygon's machinery directly, independent of `ROUND_GENERATOR`) and the generic facility-scoring/assignment contract are both untouched by this migration.

## Polygon convergence follow-up (2026-08-28)

Root-caused and fixed two mechanisms behind the p95-latency and count=5-reliability gaps identified above, then re-measured on the same commit. **Result: `v1` still remains the default**; both gates improved but neither closed.

**Root cause 1: wasted latency from a scale-correction plateau.** Instrumenting `polygon_loop._tune_waypoints`'s correction loop showed that in hard scenarios (e.g. "Inwood Hill Park, 8mi"), 4-5 of the 10 templates rebuild the identical route on every correction attempt after the first, because their rotation points toward the edge of the routable graph (a peninsula's water boundary). The synthetic anchor keeps moving further away as `scale` grows, but `_NodeIndex.nearest()` keeps snapping it to the same boundary-closest node no matter how far out it's requested (scale 1.5/2.0/2.2/3.0/5.0 all snapped one anchor to the same graph node, 1461m from start, while the synthetic point moved from 4.8km to 16km away). Roughly 23-25% of all rebuild attempts in hard scenarios were spent chasing a target that orientation cannot reach at any scale (vs ~3% in easy scenarios). Simpler alternatives were ruled out first: per-template calibration only marginally changed yield (51.9%->56.1%, "scenarios below 3 in-tolerance" unchanged), raising `max_correction_attempts` from 4 to 20 didn't move 3 of 4 stuck templates at all, and substituting each stuck template's antipodal (rotation+180) orientation was unreliable, helping some cases and making others measurably worse.

**Fix 1**: `_tune_waypoints` now stops correcting a template once two consecutive attempts build a near-identical distance (`PLATEAU_DISTANCE_EPSILON_M`) and an identical node path, keeping whatever `best` attempt it already found. This is a pure latency win with no effect on which candidate a plateaued template returns, since the tracked `best` is unchanged by stopping early. Distance similarity alone isn't sufficient: on a grid-like street network two different routes can coincidentally land on the same length while the template is still converging, so the node path (the actual graph route, already available from `_build_loop_via_waypoints`) is what actually proves the route, not just its length, hasn't changed. This hardening changes neither the full-suite p95 (2.241s -> 2.245s, within run-to-run noise) nor round count=5 reliability (93.3% -> 93.3%, identical) on the same commit; the false-positive case it guards against didn't skew the measured numbers in practice.

**Root cause 2: a bug in diverse candidate selection.** `orchestration.plan_routes`'s non-mix path called `select_diverse` once over the whole ranked candidate pool. `select_diverse`'s greedy scan, on finding a higher-ranked candidate skipped for overlapping an already-picked one, kept walking down the ranked list for any non-overlapping replacement, including one from a strictly worse `_constraint_tier` (outside distance tolerance), before ever reconsidering the skipped, same-tier candidate. For "Inwood Hill Park, 8mi" at count=5, the pool had exactly 5 in-tolerance candidates (errors 6/15/43/53/87m), but two of them (15m and 43m) traced near-identical streets (0.813 Jaccard overlap; narrow topology has only one viable corridor), so the 43m candidate was skipped and the scan reached all the way to an 801m-error candidate to fill the 5th slot, swapping a passing route for a failing one.

**Fix 2**: added `orchestration._select_diverse_within_tiers`, applying `select_diverse` within each `_constraint_tier` instead of across the whole pool. This mirrors `_select_mix_portfolio`'s tier-by-tier pattern (same guarantee, minus shape allocation), so a candidate can only be picked in place of one from its own tier, never a better one. It's a general correctness fix that benefits v1 candidates too, not polygon-specific, and doesn't touch facility matching, assignment, or `FacilitySpatialIndex`.

**Full 537-scenario suite, same commit, before vs after both fixes** (`scripts/benchmark_suite.py`, count=5):

| Metric | v1 (unchanged) | polygon (before this follow-up) | polygon (after) |
|---|---|---|---|
| p95 latency | 1.498s | 2.295s | 2.241s (**still FAILS <2.0s**) |
| Within +/-100m | 537/537 (100.0%) | 536/537 (99.8%) | 536/537 (99.8%, unchanged) |

The remaining p95 overage comes from the same doubly-expensive scenario class as before (e.g. "Battery Park tip, huge target": 2.144s polygon-alone here, still near the historical v1-alone cost of ~1.3-1.8s for the same scenario). Both generators are independently expensive there, and the plateau fix only removes wasted work, not the floor cost of the templates that do converge plus the v1 fallback this scenario still needs.

**Count reliability, real `plan_routes` path, same commit** (`scripts/benchmark_count_reliability.py`):

| Metric (round shape) | v1, count=3 | polygon, count=3 | v1, count=5 | polygon, count=5 (before) | polygon, count=5 (after) |
|---|---|---|---|---|---|
| All returned within +/-100m | 100.0% | 100.0% (unchanged) | 99.4% | 90.0% | **93.3% (still FAILS >=98.5%)** |
| Candidate within-100m rate | 100.0% | 100.0% | 99.9% | 97.6% | 98.4% |

Fix 2 (tier-aware selection) improved count=5 reliability by 3.3 points, recovering cases where enough in-tolerance candidates existed but were being incorrectly displaced. It can't manufacture a 5th in-tolerance candidate in scenarios where fewer than 5 templates converge natively at all; that's a yield ceiling, not a selection-order bug. Closing the remaining gap needs either a deeper change to polygon's own template search (e.g. asymmetric per-leg scaling instead of uniform rectangle scaling, so a template's blocked leg doesn't force the whole loop short) or a larger v1 fallback, both out of scope for this follow-up.

**Geometry** (`scripts/benchmark_polygon_loop.py`): unchanged (isoperimetric quotient 0.160->0.465, elongation 5.13->1.41, radial exposure 0.404->0.299, identical to the original migration's numbers). Neither fix touches geometry: the plateau fix returns the same `best` candidate just faster, and the tier fix only reorders which already-scored candidates are kept.

**Facility benchmark**: re-run and unchanged from the documented baseline (Stratum A 117/117, Stratum B 18/18 -> 0/18 -> 0/18 -> 0/18 at 2.8% partial, Stratum C 12/12). Confirms the plateau fix, which shares machinery with the constrained round planner, introduced no regression there.

**Decision: `v1` remains the default.** Both remaining gates (p95 latency, count=5 reliability) are real and weren't closed by this follow-up, despite exhausting the plausible smallest-fix options: per-template calibration, wider correction budgets, antipodal substitution, plateau detection, tier-aware selection. Closing them would need either an architectural change to polygon's template search or a larger fallback, both out of scope here. `ROUND_GENERATOR=polygon` remains a fully-tested opt-in with better, if not fully closed, numbers than before this follow-up.

## Adaptive round-generator policy (PR #29, 2026-08-28)

The two follow-ups above each tried to make one generator win at every supported count, and neither closed both gates: polygon's full-suite p95 (2.241s+) stayed above the <2.0s gate, and its count=5 round reliability (93.3-93.9% all-within-tolerance) never closed v1's ~99.4% baseline. A third attempt (an unmerged, closed experiment, `perf/polygon-topology-adaptive`) tried axis-scaled per-leg template refinement to close the count=5 gap directly. It nudged reliability from 93.3% to 93.9% but made full-suite p95 worse (2.245s+), trading one gap for a bigger one, so it was closed without merging. Its branch and history remain on GitHub as a record, but none of its code is in this codebase.

This PR takes a different approach: polygon is better at the product's count=3 default and v1 is better at count=5, so pick the generator per request based on the count actually asked for, instead of forcing one generator to cover both. Doing that required fixing a bug this approach would otherwise inherit: `facilities.orchestration.natural_match_pool` requests an intentionally overcomplete candidate pool for its own downstream diversity/portfolio selection (9 candidates for a count=3 no-facility request, 12 for a count=3 request with facility requirements; see [`architecture.md`](architecture.md#candidate-generation)), and before this PR that inflated pool size was the only count `generate_routes` ever saw. Selecting a generator off it would have picked v1 for the product's count=3 default the moment facility requirements were present. `generate_routes` (and `_round_pairs`/`_round_generator_version` beneath it) now take an explicit, separate `requested_count` parameter that always carries the user's real `RouteRequest.count`, independent of whatever pool size is being constructed. `tests/generation/test_round_generator_seam.py` covers this at every layer: unit-level `_round_generator_version` calls, `generate_routes` calls with pool sizes 3/9/12 all mapped to `requested_count=3`, and `natural_match_pool` itself, monkeypatched, asserting the pool-size vs `requested_count` split for both its no-facility and with-facility branches.

**Policy**: `ROUND_GENERATOR=auto` (the new default, including when the variable is unset) selects polygon when `requested_count<=3`, v1 when `requested_count>=4`. `=v1`/`=polygon` force a single generator regardless of `requested_count`. An explicitly invalid value falls back to `v1`. An operator who wants the pre-PR-29 behavior back sets `ROUND_GENERATOR=v1` explicitly. Applies to explicit `shape="round"` and `shape="mix"`'s round component identically (same seam as before); `shape="out_and_back"` and the constrained multi-facility round planner (which already used polygon's machinery directly, independent of this flag) are both untouched.

**Same-commit benchmarks of the `auto` policy itself** (not polygon-at-count=5 mislabeled as the product default, and not inferred from aggregate numbers alone: `tests/generation/test_round_generator_seam.py` plus an ad-hoc instrumented run below directly assert which generator ran):

*Count reliability, real `plan_routes` path* (`scripts/benchmark_count_reliability.py`, three back-to-back same-commit runs: [auto](../backend/benchmarks/local/count_reliability_20260828_215436.md), [v1](../backend/benchmarks/local/count_reliability_20260828_220139.md), [polygon](../backend/benchmarks/local/count_reliability_20260828_221100.md)):

| Metric | auto, count=3 | v1, count=3 | polygon, count=3 | auto, count=5 | v1, count=5 | polygon, count=5 |
|---|---|---|---|---|---|---|
| round: exact-count | 100.0% | 100.0% | 100.0% | 98.3% | 98.3% | 100.0% |
| round: all-within-100m | 100.0% | 100.0% | 100.0% | **99.4%** | 99.4% | 93.3% |
| round: p95 latency | 1.448s | 0.905s | 1.481s | 0.939s | 0.934s | 1.518s |
| ALL shapes: all-within-100m | 100.0% | 100.0% | 100.0% | 99.6% | 99.6% | n/a (round-only regression) |
| ALL shapes: p95 latency | 1.411s | 0.896s | 1.481s | 0.930s | 0.916s | n/a |

`auto`'s count=3 numbers match forced-`polygon`'s count=3 numbers, and `auto`'s count=5 numbers match forced-`v1`'s count=5 numbers, within measurement noise: direct evidence that `auto` exercises the intended generator at each count. All gates pass: count=3 exact-count 100%/all-within 100%/p95<2.0s; count=5 all-within 99.4% (>=98.5% gate, matching v1's own baseline, well above forced-polygon's 93.3%).

*Full 537-scenario suite* (`scripts/benchmark_suite.py`, which hardcodes `count=5`; [report](../backend/benchmarks/local/report_20260828_223326.md)): under `auto` this routes through v1 for that count, giving p95=1.505s (passes the <2.0s gate, matches v1's ~1.5s baseline, not polygon's 2.24s+) and 537/537 within-tolerance. That's expected: this suite has never exercised count=3, so it doesn't say anything about polygon's geometry for the actual count=3 product path.

*Geometry* (`scripts/benchmark_polygon_loop.py`, generator-level, count-independent; [report](../backend/benchmarks/local/polygon_loop_v1_vs_v2_20260828_221249.md)): unchanged from prior migrations (isoperimetric quotient 0.160->0.465, elongation 5.13->1.41, radial exposure 0.404->0.299). Since `auto` selects polygon deterministically at `requested_count<=3`, this is `auto`'s own count=3 geometry, not a separate claim.

*Facility requests* (`scripts/benchmark_facilities.py` under `ROUND_GENERATOR=auto`, `count=3` throughout; [report](../backend/benchmarks/facilities/report_20260828_222747.md)): Stratum A 117/117, Stratum B 18/18 -> 0/18 -> 0/18 -> 0/18 (the known 2+ simultaneous-requirement boundary, unchanged), Stratum C 12/12, matching the documented baseline exactly. An instrumented check spying on `polygon_loop_pairs`/`round_pairs` directly confirmed `auto` selects polygon for round/mix's round component at `requested_count=3` in all 6 representative scenarios (round and mix, x 0/1/2 facility requirements, where the internal pool inflates from 9 to 10-12 candidates as requirements are added): `polygon_calls>=1` and `v1_calls==0` in every case, end-to-end latency 0.26-0.33s. The pool-size/requested_count fix holds under real facility load, not just in isolated unit tests.

**Decision: `auto` is now the default.** Every acceptance gate passed on same-commit evidence: count=3 (the product default) exact-count/within-tolerance both 100%, p95 well under 2.0s and matching polygon's own numbers; count=4/5 all-within-tolerance at v1's own ~99.4% baseline, comfortably above the 98.5% floor; full-suite and facility benchmarks show no regression. `ROUND_GENERATOR=v1` is available as an immediate rollback (single env var, no code change) if a production issue surfaces; `ROUND_GENERATOR=polygon` forces polygon at every count for further experimentation.

## How to read the numbers

| Claim | Means | Does not mean |
|---|---|---|
| 537/537 (core suite) | Every scenario had at least one qualifying route | Every generated candidate was flawless |
| 117/117 (Stratum A) | The matching/assignment mechanism correctly recognizes an achievable facility constraint | Arbitrary real facility combinations are always jointly routable |
| 18/18 → 0/18 (Stratum B) | A single hard requirement is reliably recovered; 2+ simultaneous ones aren't today | The planner never finds partial solutions to harder requests |
| 12/12 (Stratum C) | That specific narrow water-data sample passed | All water windows everywhere in Manhattan are covered |

## Reproducing benchmarks

All three suites are deterministic Python scripts, run without arguments from `backend/`:

```bash
python scripts/benchmark_suite.py          # core local-engine suite
python scripts/benchmark_count_reliability.py
python scripts/benchmark_facilities.py
```

For interpretable timing figures, run a suite alone rather than alongside other CPU-heavy processes. These are wall-clock latency measurements, and unrelated load on the same machine will inflate them.
